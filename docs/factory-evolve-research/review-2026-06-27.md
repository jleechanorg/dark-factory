## What dark-factory actually does wrong today

### 🔴 #1 — Factory is currently broken in flight (the meta-failure)

`git log --all --oneline | grep -i exhausted` returns 14+ WIP commits, every one of the form:

```
WIP: dark-factory exhausted at <run_id> <head_sha>
Auto-recovery commit. no_progress_max=2 reached on node 'fix'
```

Recent examples (2026-06-27, last 90 minutes):
- `1d74023` `b0b15454c067` → `54c878b32999`
- `54c878b` `753d4e1c7900` → `ba034ff92f9d`
- `ba034ff` `b4648799c8f3` → `8033e9b64f28`
- `1cb61f0` `376c36e2445c` → `8fe6a976cbb8`
- 11 more going back

What this means: the factory's `fix` node is producing identical-or-no-progress output across consecutive visits, the `no_progress_max=2` short-circuit trips, and the engine auto-commits whatever was on disk (with the WIP message). The factory is **not converging** — it's been re-recovering on the same failure for weeks.

**A codex terminal review would catch this in 10 seconds** by running `git log --all --oneline | grep -c exhausted` and seeing the count.

### 🔴 #2 — `_last_output` truncation removed (recent WIP `1d74023`)

`runner/engine_run.py:137` was changed from `attempt.output[:4000]` to `attempt.output` (full output). On its face this is "let the fix prompt see the full reviewer output." But the fix prompt template at `prompts/slim/fix.md` references `${state._last_output}` — which is fine, but a 50K reviewer output dumped into the fix prompt can blow past the LLM context window for `agy` (smallest of the four backends). This is a regression introduced by the very WIP commit the factory auto-recovered on. **No reviewer caught it because no reviewer ran** (the run exhausted before the reviewer visited the new code).

### 🟠 #3 — G7 vendor collapse is still possible on factory graphs

```
$ grep -l prefer_adversarial pipelines/factory/*.dot pipelines/slim/*.dot
pipelines/slim/review_pr.dot    ← set on reviewer node
pipelines/slim/spec_gen.dot     ← set on review_main + review_attractor
```

`pipelines/factory/gates.dot`, `pr_gates.dot`, and `level5_feature.dot` **do not set `prefer_adversarial="true"` on the gate nodes**. With this default, on a `claude` run, the `gate_es` / `gate_er` / `gate_cs` nodes will resolve to `claude-sonnet` — the same vendor as the coder. The codex cold review's "different vendor" property is structurally absent from the factory's named gates.

`_resolve_gate_backend` (`runner/handler_dispatch.py:361`) confirms: prefer_adversarial is read from `node.attrs.get("prefer_adversarial", False)` — default False. The fix from the 2026-06-22 docs was "make `prefer_adversarial` default-on for any gate" — **never landed**.

### 🟠 #4 — G6 `warn → success` is still the default

`runner/handler_verdict.py:30`: `"warn": "success"`. `gate_strict` is opt-in via per-node attribute. None of the four factory pipelines set `gate_strict="true"` on any node. A `warn` verdict with three real blockers passes the gate and routes to `exit` (or to `fix` only because the *next* gate's `outcome!=success` triggers it, not the warn itself).

This is the exact bug that PR #87 (merge `216d3ce`) was supposed to fix via F6 `gate_strict` opt-in. The opt-in shipped, but the factory graphs never opted in.

### 🟠 #5 — G8 no exit SHA re-pin

`runner/handler_verdict.py:66-77` binds verdict at gate entry. The four-gate chain `holdout -> gate_skeptic -> adversarial_reviewer -> gate_es -> gate_er -> gate_cs -> exit` has no terminal re-pin. A concurrent commit between gate_er entry and the run's exit is invisible. The pipeline says "graded `head_sha` X" but doesn't say "graded the final merged `head_sha`."

`engine_run.py:359` does have `_edges._attr_int(current, "no_progress_max", 0)` but it's a per-visit hash dedup, not a global HEAD re-pin.

### 🟡 #6 — Fix-loop bound is `max_visits` on visits, not on outcomes

Per `project_2026-06-22_darkfactory_failure_root_cause.md` D3: `max_visits="3"` counts visits, not distinct outcomes. A `fix` node that produces different text but the same effective result every time still uses all 3 visits. This is why `no_progress_max` had to be added as a secondary tripwire — but as the 14+ exhausted commits show, even that doesn't catch every failure mode (it catches only when the output *hash* repeats).

### 🟡 #7 — G9 unit-only evidence accepted on graphs without holdouts

`pipelines/slim/bugfix_noholdout.dot`, `pipelines/slim/minimal_research.dot`, `pipelines/slim/review_pr.dot` have no `holdout_eval`. The `gate_er` review trusts the bundle's own claims. There is no behavioral re-execution path on these lanes.

### 🟡 #8 — G3/G5 prompt templates are open-ended but prompt-substitution audit doesn't gate them

`runner/prompt_substitution_audit.py` (PR #99) audits wiring, resolution, and min-content. It does NOT audit prompt *quality* — i.e., whether `prompts/slim/review.md` is the same whole-diff agentic review it claims to be. The G3 (templated checklist) and G5 (scope-limited-to-diff-hunk) gaps are prompt-shape issues that the audit module structurally cannot detect.

### 🟡 #9 — Fix prompt reads `_last_output` but loses reviewer rationale

`prompts/slim/fix.md` says:
```
Previous node result (free-form output from the gate/reviewer/tool that routed here):
${state._last_output}
```
The fix prompt gets the raw reviewer output, but it doesn't get the structured verdict token, the Coder Handoff section from `review.md` (just added in commit `54c878b`), or the gate_es/gate_er structured findings. The fix prompt and the reviewer prompt are not contractually coupled.

### 🟢 #10 — `level5="true"` is enforced by graph attribute but not by CI

`pipelines/factory/level5_feature.dot` has `graph [level5="true"]` and the canonical design (memory `project_2026-06-22_g3_closure_dynamic_node_design.md`) says `bin/conformance validate` should enforce it. The shipped implementation wires `runner.graph_audit` into CI for G1+G2 but not for the G3 closure / Level-5 attribute.

**Each of these is structural — a `codex exec --yolo` looking at the repo today with a 30-minute budget would catch all of them in one pass.** None of them is what the factory's in-pipeline reviewers caught, because:

1. The factory's `gate_er` is *evidence-only* — it audits evidence bundles, not implementation behavior.
2. The factory's `gate_cs` is *checklist-only* — it audits ZFC / RCF / clean-code axes, not graph-correctness.
3. The factory's `gate_skeptic` runs only when the run hasn't already exhausted, which the WIP commits show is increasingly rare.
4. The factory's `_codergen` reviewer (`prompts/slim/review.md`) has whole-diff injection (`${diff}`) and active tool-use, but it is *inside* the same fix-loop that's exhausting — i.e., it never gets to run on the WIP commits that fix itself, because the run terminates first.

This is the meta-finding: **the factory's reviewers cannot review the factory, because the factory cannot converge on its own implementation**. The same Attractor pattern that drives code production also blocks self-review. A cold `codex exec` from outside the loop is the only mechanism that can audit the loop itself.
